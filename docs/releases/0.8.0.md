# Tickler 0.8.0

Two changes you can see: Tickler offers its own updates, and the board's left
rail spends the height it has instead of guessing at it.

## Tickler updates itself from a button

Moving to a new version meant uninstalling and reinstalling the plugin, which
throws away its config row — the token thresholds and everything else in the
gear panel had to be entered again. Paperclip's Plugin Manager has no update
button, though the server has had the endpoint all along.

Tickler now checks npm for a newer version of itself and offers it in two
places:

- an **Update to x.y.z** chip in the page header, and
- the first row of the gear panel, which also names the version you are on and
  what the check found (`Up to date`, `Could not check npm…`, or
  `Installed from a local checkout`).

Pressing it upgrades in place through the host's own upgrade endpoint: npm is
re-installed, the manifest is re-read, and the plugin re-registers against the
existing config row, so your settings survive. The page then reloads onto the
new build.

Details worth knowing:

- **Instance admins only.** Everyone else sees no chip.
- **Silent when npm cannot be reached.** The check is a browser request to the
  registry, and anything it cannot answer renders nothing rather than a button
  whose version was a guess.
- **A local-path install stands down.** There the **Reload** chip still owns
  updates — an npm upgrade would replace your checkout.
- **A version that declares a new capability still needs a reinstall.**
  Paperclip grants plugin capabilities at install time only, so the upgrade is
  refused and says so.

This is also the release that makes the button appear at all: it only shows when
npm has something newer than what is installed, so 0.7.1 has no way to offer
0.8.0. Getting to 0.8.0 is the last uninstall-and-reinstall; from here the
button does it.

## The left rail spends the height it has

The rail used to be four cards each with its own pixel scroll cap — 256px of
Recent, 160px of Routines, and no cap at all on Orgs, so every org you watched
pushed the panes below it down until Portfolio was off the bottom of the screen.

It is now pinned to the viewport, measures itself, and gives each pane a height
of its header plus a whole number of measured rows. Everyone gets the fewest
rows worth drawing, then the surplus goes out one row at a time in rank order —
Orgs and Recent first, Portfolio and Routines equal behind them — so a short
screen is spent on the two panes worth reading. No pane ends in a row cut in
half, a pane holding rows back says `+8 more`, one the rail cannot seat falls
back to its header instead of being clipped, and a taller monitor goes into the
panes rather than into a scrollbar. The layout studies behind it are in
[docs/mockups](../mockups/README.md).

## Release tooling

Not user-facing, but it is why 0.6.0 took five attempts to publish: the npm OIDC
diagnostic no longer guesses why the registry refused. npm answers
`404 … package not found` both when a package has no trusted publisher entry and
when it has one that does not match the run, and the old message read as a
verdict it could not support. Both now say the 404 is ambiguous and name the
case that produced it, and on a refusal the script prints the claims the run
actually presents (`repository`, `repository_owner`, `workflow_ref`,
`environment`) — the half of the comparison npmjs.com cannot show. Never the
token itself.

## What you have to do

Upgrade. Nothing to migrate and no setting to change.

If you are on 0.7.1 or earlier, this one is still an uninstall and reinstall
from the Plugin Manager, and the token thresholds in the gear panel have to be
entered again afterwards. From 0.8.0 on, the **Update to x.y.z** chip does it
without losing them.
